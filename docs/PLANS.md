# PLANS.md - Spec-kit Plan Style Contract

Work is authorized by `specs/<feature>/plan.md`, generated by `/speckit-plan`
from `.specify/templates/plan-template.md`. This file keeps the writing
discipline behind that artifact. When implementing a feature, treat
`specs/<feature>/plan.md` as the source of truth.

## Frontmatter

Every `plan.md` starts with:

```yaml
---
ticket: <JIRA-KEY or none>
status: draft
covers: []
verify: <command that proves this feature works>
analyzed:
---
```

- `ticket` is a known Jira key, or `none`.
- `status` is `draft`, `active`, or `completed`. `/speckit-plan` emits
  `draft`; only a human-reviewed promotion makes it `active`.
- `covers` is a list of repository-relative path prefixes this feature may
  edit. The pre-commit sensor reads it from the git index.
- `verify` is the shell command that proves the feature works.
- `analyzed` is filled with the date the `/speckit-analyze` report was read
  before promotion to `active`.

Exactly one `specs/<feature>/plan.md` may be `active` in a worktree.

## The `covers:` field

`covers:` is a list of repository-relative **path prefixes**. Optional leading
`./` is accepted. Absolute paths are invalid. A file is "covered" if any entry
is a prefix of its path. A trailing `/` covers a directory and everything
inside it:

```yaml
covers:
  - internal/widget/
  - cmd/foo/main.go
```

This field is consumed by `scripts/harness/check_plan_coverage.py` at
pre-commit, which reads plan content from the git **index** (the staged
version) — an unstaged edit to `covers:` cannot authorize a commit. Always
allowed without coverage: anything under `docs/`, `specs/`, or
`scripts/harness/`, plus root anchors (`AGENTS.md`, `CLAUDE.md`,
`ARCHITECTURE.md`, `SECURITY.md`, `README.md`) and `.harness-version`. Staged
deletes count as edits and need coverage too. Bypass with:

```bash
HARNESS_BYPASS="<reason>" git commit ...
```

## The `verify:` field

`verify:` is the command that confirms the plan delivered working behaviour. It
is the completion gate: the plan is not done until `verify:` is green. Examples:

```
verify: go test ./... && go build ./...
verify: npm test && npm run build
```

## Style

**Prose first**, plain sentences over checklists. **Anchor on observable
outcomes** — "after `go run ./cmd/foo`, the response includes the new field" is
acceptable; "added a Model struct" is not. **Resolve ambiguity in the plan**;
don't outsource decisions to the reader. **Define terms of art** the moment you
use them, and name where they appear in the repo.
