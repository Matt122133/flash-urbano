# ADR harness-design — A lightweight harness for AI agent usage

## Status

Accepted.

## Context

Flash Urbano is a package pickup/delivery service for a single-operator
courier client (Diego). This repo builds a client-facing web app (package
creation, "About us", contact, reviews) and an admin Android app (package
triage, route planning, delivery lifecycle, dashboard). AI coding agents do
plan-driven work on it under this harness.

This is a small-to-medium tool. The goal is the *architecture benefits* of a
harness — plan-driven changes, recorded decisions, a guided workflow — without
the ceremony or vendor coupling a larger team needs. Three failure modes a
harness prevents:

1. **Drift.** Plans and decisions live in chats and ephemeral sessions;
   nothing compounds across sessions.
2. **Context.** The agent starts each session cold, not knowing what exists,
   what's in flight, or what's already decided.
3. **Scope creep.** Without a stated plan, changes sprawl beyond the task.

We adopt the mental model from Martin Fowler (*Harness Engineering for Coding
Agent Users*) and the OpenAI Codex team (*Harness Engineering*):

> Agent = Model + Harness.

The harness — the part we build around the model — raises the chance the agent
gets a task right the first time and gives a feedback loop that self-corrects
before changes reach human eyes.

## Decision

### Mental model

Every control is either a **guide** (feedforward — steers before acting) or a
**sensor** (feedback — catches after acting):

|  | Computational (deterministic) | Inferential (LLM/human-judged) |
|---|---|---|
| **Guides** | linters, formatters, LSP | `AGENTS.md`, `docs/` hierarchy, ADRs, plan template |
| **Sensors** | tests, pre-commit `covers:` check | code review, a manual second-pass review |

Plans are artifacts produced by guides, not a third control type. Active plans
live in `specs/<feature>/plan.md` — the spec-kit-generated plan artifact.

### Vendor neutrality

The harness depends on no specific agent vendor. `AGENTS.md` is the cross-agent
entry point (`CLAUDE.md` is a symlink to it). The harness logic remains
vendor-neutral even when a tool requires vendor-shaped integration files.
Agent-specific files are permitted only as integration artifacts generated by
their owning tool, such as `.claude/skills/speckit-*` and
`.agents/skills/speckit-*`. Those generated files are regenerated with the
`specify` CLI and never hand-edited. Harness-authored hook skills
(`harness-*`) live once under `.agents/skills/` and are symlinked into
`.claude/skills/`. An independent review (fresh agent, separate session, human,
or an external CLI like Codex) is encouraged but invoked manually, not wired as
a mechanical gate.

### Operating principle

**If it is not in the repo, it does not exist.** Anything the agent must reason
over must live as versioned markdown, code, or schema inside this repo.

### Phase gates

Work moves through **Brief → Decide → Plan → Execute**. No code without an
active, analyzed spec-kit plan; no edits outside the active plan's `covers:`;
not done until `verify:` is green. Encoded in `AGENTS.md`, enforced by the
plan-coverage check at pre-commit *where it's wired* (see § Sensor attachment)
and by convention everywhere else.

### Sensor attachment

The plan-coverage sensor only matters if it runs on every commit, and real
repos already have a hook manager (husky, lefthook, the `pre-commit`
framework, plain `.githooks/`) before the harness ever arrives. `core.hooksPath`
is a single git setting — the harness and an existing manager cannot both hold
it, and whichever wrote it last wins on the next `npm install` / `pre-commit
install` / equivalent. Two installs of this harness (`init-harness-speckit`
1.0.0) shipped into husky repos and both landed `UNWIRED`: the sensor was
scaffolded, its own selftests were green, and nothing called it — the repo's
`AGENTS.md` and `dev-setup.md` asserted enforcement that wasn't there.

The fix is attachment, not ownership:

- **A hook manager already owns `core.hooksPath` → the harness never takes it.**
  It appends one line to the manager's own hook file, between idempotent
  markers, and leaves `core.hooksPath` exactly as the manager set it.
- **No manager present → the harness is the manager**, via a versioned
  `.githooks/pre-commit` + `core.hooksPath .githooks`. This is the only case
  where it sets the value itself, because nothing else is claiming it.
- **The hook file is YAML/JSON config** (`lefthook.yml`,
  `.pre-commit-config.yaml`, a `simple-git-hooks` key) → the harness does not
  auto-edit it. A bad structural merge breaks every developer's commit path,
  and the harness has no way to run the result to check. It writes the exact
  snippet to `docs/HARNESS-TODO.md` instead.

None of that makes wiring *certain* — a TODO item can go unread exactly like
the doc claims did. So the sensor gained a fourth mode, `--doctor`, that
resolves the effective hook file (`core.hooksPath`, falling back to
`.git/hooks`) and reports `WIRED` / `UNWIRED` by inspecting it — a measured
fact, not an assumption. `speckit_gate.py gate` and `gate-lite` call it and
print a non-blocking warning on `UNWIRED`; the scaffold's own Step 12 report
states the doctor's actual verdict instead of asserting success. This keeps
the harness's central honesty property intact: convention is allowed to be
unenforced, but it is never allowed to be *silently* unenforced.

### Plan format

Specified in [`../PLANS.md`](../PLANS.md): one `specs/<feature>/plan.md` per
initiative, living document, with `covers:` and `verify:` frontmatter. The plan
is generated by `/speckit-plan` from `.specify/templates/plan-template.md`.

### What ships

1. `AGENTS.md` (+ `CLAUDE.md` symlink) — operating principle, hard
   constraints, phase gates, session bootstrap.
2. `ARCHITECTURE.md` — the repo's code map.
3. [`docs/PLANS.md`](../PLANS.md) — the plan style contract.
4. `.specify/` spec-kit engine, with the harness's one edit to
   `plan-template.md` (frontmatter + a Constitution Check that points at the
   constitution). The constitution itself is supreme and team-owned — untouched.
5. `.specify/extensions.yml` — registers the harness hook skills at spec-kit's
   native extension points.
6. `docs/decisions/` — ADRs (this one, `adr-slug-canonical`,
   `speckit-harness-integration`) and domain ADRs.
7. `docs/processes/harness.md` — operating manual; `speckit-loop.md` — loop
   runbook; `dev-setup.md` — stack commands and the plan-coverage check wiring.
8. `scripts/harness/check_plan_coverage.py` — the one mechanical sensor, with
   a `--doctor` mode that reports whether it's actually wired into this
   clone's pre-commit hook (see § Sensor attachment);
   `scripts/harness/speckit_gate.py` — the gate/verify/loop engine the hook
   skills call.

### Steering loop

The harness is an ongoing practice. For every agent failure, ask: *guide
missing, or sensor missing?* Extend one. "Just prompt harder" is not an answer.

## Consequences

**Positive.**
- A reviewable artifact (`specs/<feature>/plan.md`) sits between "request" and
  "shipped".
- Decisions and plans are versioned and co-located — drift drops.
- The `covers:` check keeps the agent inside the approved scope.
- Vendor-neutral: works under Claude, Codex, or any agent that reads
  `AGENTS.md`; nothing breaks when tooling changes.

**Negative.**
- Higher cost per task in the short term — a plan precedes code.
- Phase gates beyond `covers:` are enforced socially; violations are possible.
- The harness itself needs steering-loop maintenance or it decays.
- The `covers:` sensor's wiring depends on the repo's pre-existing hook
  manager cooperating; `--doctor` makes an unwired sensor *visible*, not
  impossible (see § Sensor attachment).

**Open.**
- Behavioural correctness remains a human-review + tests problem.
- A heavier, mechanically-enforced review gate is deliberately deferred — add
  it if the tool grows past the small-tool lane.
